## ⚠️ دو فایل اضافه‌شده (خارج از لیست اصلی)

چون این سایت به یک **بک‌اند واقعی با ورود/ثبت‌نام و پنل مدیریت کامل** وصل است (که در
مکالمات قبلی به‌صراحت درخواست دادید: «همه چیز... پنل ادمین کامل»)، حذف این قابلیت‌ها
باعث عقب‌گرد از کاری می‌شد که قبلاً ساخته بودیم. بنابراین دو صفحه و فایل جانبی، **خارج
از لیست اصلی درخواستی**، اضافه شد:

| فایل | چرا لازم بود |
|---|---|
| `login.html` + `assets/css/auth.css` + `assets/js/auth.js` | ورود/ثبت‌نام واقعی مشتری و ادمین (JWT) |
| `admin.html` + `assets/css/admin.css` + `assets/js/admin.js` | پنل مدیریت (محصولات، سفارش‌ها، مشتریان، آپلود چندعکسی، تغییر رمز) |

اگر اصلاً به این دو صفحه نیاز نداری و می‌خواهی سایت را واقعاً به همان ۶ فایل اصلی محدود
کنی، باید بخش «ورود» در هدر و کل پنل مدیریت از پروژه حذف شود — که یعنی دیگر نمی‌شود
محصول اضافه/ویرایش کرد مگر مستقیماً در دیتابیس. کافی است بگویید تا این کار را هم انجام دهم.

## نکته‌ی توزیع فایل‌های جاوااسکریپت

طبق لیست درخواستی فقط ۷ فایل JS وجود داشت و هیچ فایل جداگانه‌ای برای «ارتباط با API»
در نظر گرفته نشده بود. برای وفاداری کامل به همین ۷ اسم، تصمیم گرفتم:
- **`storage.js`**: هم ذخیره‌سازی محلی (سبد خرید در `localStorage`، نشست ورود در
  `sessionStorage`) و هم تابع پایه‌ی ارتباط با سرور (`apiFetch`) را نگه می‌دارد.
- **`products.js`**: علاوه بر منطق محصولات، تمام متدهای ارتباط با API (سفارش‌ها،
  مشتریان، ورود/ثبت‌نام، نظرات) را هم شامل می‌شود — چون فایل جداگانه‌ای برای این‌ها در
  لیست نبود.
- **`main.js`**: طبق ترتیب لیست شما (آخرین فایل)، نقش «چسب مشترک همه صفحات» را دارد:
  هایلایت‌کردن لینک فعال در نوبار، بروزرسانی نشان تعداد سبد خرید، و نمایش وضعیت ورود.

## چرا سبد خرید در localStorage است (نه فقط حافظه)

نسخه‌ی قبلیِ این پروژه یک تک‌صفحه‌ای (SPA) بود که هرگز واقعاً رفرش/ناوبری نمی‌شد، پس
سبد خرید می‌توانست فقط در یک متغیر جاوااسکریپت بماند. اما حالا که سایت **واقعاً
چندصفحه‌ای** است، با هر کلیک روی یک صفحه‌ی جدید (index.html → product.html →...)
تمام حافظه‌ی جاوااسکریپت از صفر بارگذاری می‌شود. بنابراین سبد خرید باید در
`localStorage` ذخیره شود تا از صفحه‌ای به صفحه‌ی دیگر باقی بماند — این یک انتخاب فنی
درست و استاندارد برای هر سایت چندصفحه‌ای واقعی است (برخلاف artifact های چت که این کار
در آن‌ها ممنوع است).

## 🔒 تقویت امنیتی: جلوگیری از XSS در innerHTML

در یک ممیزی کامل، همه‌ی جاهایی که از `innerHTML` با داده‌ی پویا استفاده می‌شد بررسی شد.
یک باگ واقعی و قابل‌بهره‌برداری (exploitable) پیدا شد: نام محصول در attribute
`alt="${product.name}"` بدون escape درج می‌شد — یعنی نامی مثل
`Evil"><img src=x onerror="alert(1)">` می‌توانست از attribute خارج شود و کد
دلخواه اجرا کند.

**راه‌حل نهایی (تست‌شده با حمله‌ی واقعی XSS در مرورگر واقعی):**
- یک تابع `escapeHTML()` در `assets/js/products.js` اضافه شد و روی **تمام** متن‌های
  پویا (نام/توضیحات محصول، نام/آدرس مشتری، متن نظرات، نام/ایمیل کاربران) قبل از درج
  در `innerHTML` اعمال می‌شود — در تمام ۶ فایل JS صفحه‌محور.
- `.escape()` از اعتبارسنج‌های بک‌اند (`express-validator`) حذف شد، چون خنثی‌سازی
  XSS باید در **نقطه‌ی خروجی/رندر** انجام شود، نه در نقطه‌ی ورودی/ذخیره‌سازی — escape
  کردن در سمت سرور باعث می‌شد داده‌ی خام در دیتابیس خراب شود و با escape سمت
  فرانت‌اند «دوبار-انکود» (double-encoding) ایجاد کند (مثلاً `&` به‌جای نمایش صحیح،
  به‌صورت `&amp;amp;` نمایش داده می‌شد).
- با Playwright واقعاً یک محصول با payload مخرب (`<script>`, `<img onerror>`,
  attribute-breakout) شبیه‌سازی و تأیید شد که هیچ کدی اجرا نمی‌شود؛ و یک محصول با
  کاراکترهای خاص واقعی (کوتیشن، `&`، علائم فارسی) هم تست شد تا مطمئن شویم متن درست
  و بدون خرابی نمایش داده می‌شود.

## راه‌اندازی

### ۱. بک‌اند را اجرا کن
این فرانت‌اند به بک‌اندی نیاز دارد که پیش‌تر ساختیم (`khanebargh-backend`). طبق
`README.md` همان پوشه:
```bash
cd khanebargh-backend
npm install
docker compose up -d
cp .env.example .env   # و مقداردهی کن
npm run prisma:migrate
npm run seed
npm run dev
```

### ۲. فرانت‌اند را با Live Server در VS Code باز کن
پوشه‌ی `HomeShop/` را در VS Code باز کن، روی `index.html` راست‌کلیک و "Open with Live
Server" را بزن (پورت پیش‌فرض ۵۵۰۰).

⚠️ اگر پورت‌ها را عوض کردی، باید هماهنگ باشند:
- `khanebargh-backend/.env` → `CLIENT_ORIGIN` = آدرس Live Server
- `assets/js/storage.js` → `API_BASE` = آدرس بک‌اند
- متاتگ CSP در بالای هر ۸ فایل HTML → `connect-src`/`img-src` = آدرس بک‌اند

## محدودیت‌های شناخته‌شده (صادقانه)
- تصاویر داخل `assets/images/products/` واقعاً استفاده نمی‌شوند — توضیح کامل در
  `assets/images/products/README.md`.
- فرم تماس (`contact.html`) فقط یک پیام موفقیت نمایش می‌دهد و به سرور ارسال نمی‌شود
  (چون بک‌اند فعلی endpoint مخصوص پیام تماس ندارد).
- این پروژه از داخل یک محیط چت نوشته شده و **به‌صورت واقعی روی مرورگر تست نشده** — قبل
  از انتشار، خودت کامل تستش کن.
